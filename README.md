# Monkey Island Website

Django-приложение для продажи VPN-подписок Monkey Island (xray/VLESS TCP Reality через remnawave панель).

---

## Структура проекта

```
engine/           — основное Django-приложение (views, models, urls)
  templates/      — HTML-шаблоны страниц
web_app/          — конфиг Django (settings, urls, wsgi/asgi)
common/           — общие утилиты (rmws_client и др.)
proto/            — gRPC protobuf-схемы для remnawave
docker/           — Docker-конфиги для деплоя (website, edge, postgres)
```

Пользовательские тексты в шаблонах должны оставаться профессиональными и
сервисными. Не используйте игровые, пиратские или морские метафоры в onboarding,
кабинете, login-flow, уведомлениях об оплате и ошибках; бренд Monkey Island
сохраняется как название продукта.

## Страницы и их логика

### `/tg-webapp/` — Telegram Mini App (кабинет в WebView бота)

Кнопка меню бота (управляется в боте командой `/webapp`) открывает эту страницу
внутри Telegram. Флоу:

1. `GET /tg-webapp/` (`telegram_webapp_entry`) отдаёт `tg_webapp.html` —
   минимальную страницу с `telegram-web-app.js`, которая берёт
   `Telegram.WebApp.initData` и отправляет его POST-ом на `/tg-webapp/auth/`.
2. `POST /tg-webapp/auth/` (`auth_by_telegram_webapp`) валидирует подпись
   `initData` (`verify_telegram_webapp_init_data`, HMAC-SHA256 с ключом
   `WebAppData` + токен бота из `TELEGRAM_AUTH_BOTS` по хосту, свежесть
   `auth_date` ≤ 24 ч), находит пользователя по `telegram_id` (или создаёт через
   `create_site_user` с `creation_channel="bot_webapp"` — запасной путь для
   пользователей без `/start`), авторизует сессию и редиректит в `dashboard`.
3. В сессии ставится флаг `tg_webapp_mode` — dashboard рендерится в режиме
   Mini App: подключается Telegram SDK (`ready()`/`expand()` +
   `disableVerticalSwipes()` + `requestFullscreen()` на iOS/Android с Bot API
   8.0, отступы статусбара — через `--tg-safe-area-inset-*`), скрываются кнопки
   «Выйти», PWA-подсказки и реферальный бейдж «+40» (`tg-webapp-hide`), оплата
   открывает платёжную страницу через `Telegram.WebApp.openLink()` (системный
   браузер) вместо `window.open`, кнопка «Оплатить» на экране тарифов
   фиксируется к низу вьюпорта, rem-базис ужимается до 15px. Mini App и обычный
   мобильный кабинет (до 1024 px) используют общую mobile-first композицию:
   компактный статус с датой окончания, одну контекстную жёлтую CTA и строки
   управления автопродлением и продлением без крупного счётчика дней и
   прогресс-бара. Нижняя навигация:
   Главная / Рефералы / Поддержка / Профиль («Установка» доступна с Главной).

Вкладка «Профиль» (внутренний id `settings`, чтобы сохранить совместимость
с прямыми ссылками) для сайта и Mini App: пункт «Часто задаваемые вопросы»
открывает суб-экран FAQ из 5 разделов и 19 вопросов (тексты согласованы с
разделом «Вопросы» бота, `handlers/faq.py`), пункт «Добавить на рабочий стол»
(в Mini App открывает кабинет в браузере через `openLink`, на сайте — модалку
PWA-инструкции), ссылки на оферту (`/offer/`) и политику (`/privacy/`).

Типографика кабинета выровнена по экрану тарифов: заголовки weight 700 без
капса. Цена «в месяц» на витринах считается фильтром
`engine/templatetags/pricing.py::floor_div` (целочисленное деление вниз:
599/3 → 199 ₽, 1799/12 → 149 ₽) — используется в dashboard и на лендингах
`index_vpn` / `index_vps` / `index_vps_direct_sale`.

Ограничение: в web-версии Telegram (web.telegram.org) mini app открывается в
iframe, где сессионные cookie с `SameSite=Lax` не работают — вход гарантирован
в нативных клиентах (iOS/Android/Desktop). Тесты —
`engine.tests.TelegramWebappAuthTests`.

### `payment_status.html` — Статус платежа

Страница опрашивает backend по API (`status_api_url`) каждые 2.5 секунды и отображает одно из трёх состояний:

| Состояние | `data-status` | Поведение |
|-----------|---------------|-----------|
| **pending** | `pending` | Компактный орбитальный индикатор, шаги процесса, повторное открытие формы и возврат в кабинет |
| **succeeded** | `succeeded` | Зелёный чекмарк, редирект в ЛК через 1.2 с |
| **failed** | `failed` | Красный индикатор, сообщение об ошибке |

**Логика polling:**
```js
async function pollStatus() {
    // GET status_api_url + window.location.search
    // При pending → повторить через 2500ms
    // При succeeded/failed → остановить опрос
    // При сетевой ошибке → повторить через 3500ms
}
```

**Контекстные переменные Django:**
- `initial_status` — начальное состояние (`pending` / `succeeded` / `failed`)
- `initial_message` — сообщение об ошибке (для failed)
- `login_url` — URL личного кабинета
- `payment_url` — URL формы оплаты для кнопки «Продолжить оплату» при pending
- `status_api_url` — API-эндпоинт для polling
- `support_telegram_url` — ссылка на Telegram-поддержку

#### Состояние pending — орбитальный индикатор

Вместо простого спиннера используется многослойная анимация:
- **`.orb-ring-outer`** — внешнее кольцо, вращается по часовой (1.6 с, eased)
- **`.orb-ring-inner`** — внутреннее кольцо, вращается против часовой (1.1 с, linear)
- **`.orb-pulse`** — пульсирующий ореол, затухает наружу (2.2 с)
- **`.orb-center`** — центральный круг с "дыханием" (scale 1→1.05, 2.8 с)
- Шаги процесса: «Оплата отправлена ✓» → «Ожидаем подтверждения ⟳» → «Активация подписки»
- Кнопка «Вернуться в кабинет» использует `location.replace('/dashboard/')`,
  поэтому пользователь не попадает обратно на pending-экран по кнопке браузера
- В Telegram Mini App тот же возврат доступен через нативный `BackButton`

При переходе в `succeeded` кольца останавливаются, центр становится зелёным с `✓`.
При переходе в `failed` кольца останавливаются, центр становится красным с `!`.

Опрос статуса (`pollStatus`) намеренно идёт без таймаута, пока пользователь остаётся
на странице: при `succeeded` она бесшовно переадресует его в личный кабинет
(`login_url`). При этом пользователь может явно вернуться в кабинет, если решил не
продолжать оплату. Возврат не отменяет инвойс и не меняет статус платежа: если оплата
всё же завершится, вебхук по-прежнему активирует подписку.

**Источники статуса оплаты.** Базово статус берётся из БД (`get_purchase_payment_status`):
`YkPayment` / `WataTransaction`, которые пишет вебхук платёжного сервиса. У Wata экран
успеха держит пользователя ~10 секунд перед собственным редиректом, а вебхук может
прийти не сразу — поэтому есть **активная проверка статуса напрямую у Wata**:

- `fetch_wata_transaction_status(order_id)` (`engine/payments.py`) — read-only
  `GET {WATA_HOST}/transactions?orderId=…` с `Bearer WATA_TOKEN`; возвращает
  `Paid` / `Declined` / `None`. Успехом считается ТОЛЬКО явный `Paid`; при любой
  ошибке/таймауте/лимите → `None` (откат к поведению по вебхуку).
- Эндпоинт `GET /payment/status/<token>/active-json/`
  (`payment_status_active_json`) — то же, что `…/json/`, но при `pending`
  дополнительно спрашивает Wata. Обращения к Wata троттлятся (1 раз в 30с на заказ:
  у Wata GET лимитирован 1/30с на объект, см. их доки).
- Формы оплаты на лендингах и в кабинете перехватывают submit: текущая вкладка
  переходит на `payment_status`, а hosted page Wata/YooKassa открывается в новой
  вкладке. `/pay/` для такого запуска отвечает JSON (`payment_url`,
  `payment_status_url`) и дополнительно сохраняет `payment_url` в сессии, чтобы
  на странице статуса можно было повторно открыть форму оплаты, если браузер
  заблокировал новую вкладку.
- Wata/YooKassa hosted page открываются без iframe. Это важно для СБП: сайты банков
  часто запрещают встраивание во фрейм, поэтому выбор банка внутри iframe ломается.
  После оплаты провайдер возвращает пользователя на нашу `payment_status`.
- Фискализация (54-ФЗ): YooKassa-платёж создаётся с объектом `receipt`
  (`engine/payments.py::build_receipt`, ставка «без НДС» `vat_code=1`,
  `payment_subject=service`); чек уходит на email пользователя — на сайте он
  есть всегда (логин кабинета). WATA-платежей это не касается.

**Важно (безопасность):** сама `payment_status` и редирект в кабинет остаются
завязаны на вебхук — он не только подтверждает оплату, но и активирует подписку.
Иначе пользователя можно увести в кабинет раньше активации подписки («оплатил, но
нет доступа»).

### `dashboard.html` — Личный кабинет

Единственный шаблон личного кабинета. Параметр `?ui=v1` больше не поддерживается.
SPA-like дашборд с вкладками (home / setup / profile / support / settings).
Адаптивный: десктоп — боковое меню 248px, мобайл — нижний nav-bar.
Шаблоны кабинета и PWA manifest явно задают темную `theme-color`/`color-scheme`,
чтобы iOS Safari и standalone-режим не подсвечивали системные зоны светлым цветом.
Для iOS standalone в `dashboard.html` есть отдельный safe-area фикс: контент получает
верхний отступ под status bar, а нижний nav-bar не резервирует лишнюю высоту под
несуществующую браузерную строку.

Личный кабинет поддерживает новый инвариант: запись в SQLAlchemy-таблице `users`
может существовать без RWMS-подписки. В этом случае кабинет показывает состояние
«Нет активной подписки», скрывает ключи подключения и ведёт пользователя к оплате.
После успешной оплаты платёжный сервис активирует/создаёт RWMS-подписку для того же
`users.username`, и кабинет начинает показывать ключи и мастер настройки.

В `dashboard.html` аккаунт без активной подписки сначала попадает не в обычный
дашборд, а на компактный экран выбора тарифа с преимуществами и оплатой. Обычный
интерфейс кабинета, мобильное меню и реферальная плавающая кнопка в этом состоянии
скрыты.

Экран «Продлить/Купить подписку» (`#tariff-selection-view`, открывается по кнопке
«Продлить» через `showTariffs()`) адаптивный:
- **на телефоне** — радио-список тарифов в том же стиле, что и экран оплаты
  (`.plans-*` / `.plan-row`): блок преимуществ (обход белых списков, YouTube без
  рекламы, безлимит, до 15 устройств), цена за месяц, одна кнопка «Оплатить»;
- **на десктопе** — прежние 3 карточки тарифов (формат оставлен как был), но в
  каждую добавлены 4 ключевых преимущества, цена за месяц и блок снижения страха
  оплаты: гарантия возврата за 3 дня, иконки Visa/MC/Mir/СБП и пояснение, что после
  оплаты ключи откроются прямо в кабинете.

**Вкладки:**
- **home** — в desktop web-кабинете статус подписки, прогресс-бар и быстрые действия. Карточка статуса
  (`.status-overview-card`) построена по простой иерархии: подпись «Подписка» →
  крупное число оставшихся дней с единицей (`time_left_value` + `time_left_unit`,
  напр. `958 дн.`) → строка «Активна до ДД.ММ.ГГГГ» (зелёная) → прогресс-бар →
  статус автопродления. Для аккаунта без активной подписки та же карточка
  показывает «Доступ не оплачен» и кнопку «Купить подписку». На мобильном сайте
  и в Mini App вместо неё показывается `.tg-mini-home` с одной основной CTA и
  компактными строками действий; состояния CTA зависят от доступности и
  скорого окончания подписки. На desktop главная больше не дублирует боковое
  меню карточками «Установка», «Поддержка» и «Рефералы»: рядом с основной
  кнопкой «Продлить» находится компактная вторичная кнопка «История платежей»,
  открывающая существующий `#payments-history-sheet`. Та же пара действий
  сохраняется в предупреждении о скором окончании подписки. Desktop-слой
  (`@media (min-width: 1025px)`) использует Inter и компактные прямоугольные CTA
  с радиусом 8px. Активный раздел бокового меню получает спокойный серый фон и
  вертикальную жёлтую полосу вместо жёлтой pill-кнопки. Плавающий бейдж `+40`
  заменён нижней плашкой «Пригласите друга». На desktop она открывает отдельный
  центрированный `#ref-desktop-content`: окно показывает цепочку из трёх условий,
  статистику приглашений, ссылки для Telegram и сайта, копирование и безопасную
  отправку через `t.me/share/url`. На ширине до 1024px и в Mini App сохраняется
  прежний мобильный `#ref-content` в формате bottom sheet. Оба представления
  используют те же серверные ссылки, счётчики и настройки; максимум бонуса
  выводится как сумма трёх действующих настроек реферальной программы. В desktop
  dialog круглые пиктограммы этапов сохраняют flex-центрирование, а readonly
  ссылки отображаются обычным текстом без общего чёрного фона полей ввода.
  Карточка «Заработано» выровнена под отдельным крестиком в правом верхнем углу,
  её подпись и значение центрированы как в desktop-концепте; оба правых элемента
  позиционируются независимо от сетки, а компактная высота шапки не оставляет
  пустую полосу перед блоком условий. Все
  реферальные поверхности используют фирменную чёрно-жёлтую палитру: жёлтые
  иконки, акцентные рамки и основные CTA вместо фиолетовых элементов. API,
  схема БД, начисление бонусов и платёжная логика при этом не меняются.
  Главная desktop-версия использует семантическую тональную иерархию без смены
  структуры: карточка подписки получила глубокую графитовую поверхность с
  тёплой янтарной подсветкой, мелкой золотой шумовой текстурой под радиальной
  маской и зелёным прогрессом, продление — холодный
  графитовый фон и нейтральную кнопку истории, а реферальная плашка — сдержанный
  бронзово-чёрный оттенок. Жёлтый остаётся цветом основных CTA и выбранного
  раздела, поэтому фирменный стиль сохраняется без однообразной заливки.
- **setup** — вкладка «Установка»: подключение по платформам (см. ниже)
- **profile** — вкладка «Приглашения и бонусы». Кабинет показывает три компактные
  карточки бонусов рефереру: регистрацию друга (`join_referrer_bonus_days`),
  расход трафика (`traffic_referrer_bonus_days`) и покупку
  (`purchase_referrer_bonus_days`); статистические карточки на этой вкладке тоже
  используют компактную высоту без общего `metric-card` min-height. Кнопка
  «Условия» открывает отдельный `#referral-terms-modal`, а не общий PWA-модал:
  на desktop это центрированное окно с тремя компактными строками, на мобильном
  сайте и в Mini App — bottom sheet с вертикальным таймлайном, свайпом вниз и
  закреплённой жёлтой CTA; на desktop нейтральная кнопка «Понятно» использует
  контрастный белый текст. Окно закрывается по фону, кресту, `Escape` и
  Telegram BackButton; значения и максимум бонусов берутся из действующих
  серверных настроек реферальной программы.
- **support** — чат поддержки
- **settings** — вкладка «Профиль» (контурная иконка пользователя в боковом и
  нижнем меню; технический id сохранён для обратной совместимости).
  Сгруппированы аккаунт и сервис: строка **Telegram** (статус «Подключён» либо
  кнопка «Подключить» по `tg_bind_link`), строка **Почта** с кнопкой
  «Сменить»/«Указать» (открывает тот же лист `openEmailBindSheet()`, что и на home),
  ссылка **Поддержка** (`support_telegram_url`), аккордеон **FAQ** (`.faq-item`,
  раскрытие через `toggleFaq()` / CSS-класс `.open`), кнопка
  **«История платежей»** (внизу, над «Выйти») и **«Выйти»».

  **Отключение автопродления сознательно убрано с видных мест** (главный экран
  mini app и заметная карточка в профиле заменены на «Историю платежей»):
  отмена живёт маленькой серой ссылкой внизу листа `#payments-history-sheet`
  (видна всегда — есть ли что отменять, решает `onAutopayButtonClick` по
  `HAS_RECURRENT`). FAQ описывает этот путь
  (Профиль → История платежей → «Отключить автопродление»).

  **История платежей**: лист `#payments-history-sheet`
  (`openPaymentsHistorySheet()`), данные — `GET /cabinet/api/payments/`
  (`cabinet_payments_history`): только успешные оплаты текущего пользователя
  (YooKassa `succeeded` + WATA `Paid`), свежие первыми, до 100 строк.

  Ссылка отмены запускает прежний флоу (`onAutopayButtonClick()`): JS смотрит
  на флаг `HAS_RECURRENT` (= `has_recurrent`), источник истины —
  `yk_recurrent_payments` (Wata рекурренты не поддерживает):
  - **есть рекуррент** → лист-подтверждение (`#autopay-sheet`, objection как у бота)
    → «Всё равно отключить» → `POST /cancel-autopay/`;
  - **рекуррента нет** → информационный лист (`#no-autopay-sheet`,
    `openNoAutopaySheet()`) «Автопродление не подключено — отменять нечего».

  На случай гонки (рекуррент отменён в другом месте между загрузкой страницы и
  подтверждением) бэкенд возвращает `removed_recurrents`; при `0` фронт тоже
  показывает информационный лист вместо тоста об отключении. Успешная отмена
  пишет в `event_logs` то же событие, что и бот
  (`confirm_cancel_autopay_clicked`), — иначе отмены из кабинета были бы
  невидимы для churn-аналитики и ежедневного отчёта.

В десктопном сайдбаре внизу есть отдельная кнопка «Выйти».

Клиентские тексты личного кабинета должны обращаться к пользователю в уважительной
форме: «Вы», «ваш», «выберите», «установите». Не смешивайте их с формами на «ты».

Action-кнопки кабинета (`setup-cta-btn`, `setup-link-btn`, `payment-cta`,
`quick-access-btn`, кнопки копирования) визуально приведены к одному CTA-стилю:
желтый фон `#ffc700`, радиус 14px, шрифт 15px/700, обычный регистр и тень как у
«Подключиться в 1 клик».

**Флоу установки (`setup`).** По умолчанию (`USE_NEW_SETUP_FLOW=false`) показывается
компактный одноэкранный флоу в духе телеграм-бота — «от простого к сложному»
(`#setup-logic-placeholder`, JS `setPlatform`/`setApp`, данные `installData`):
- При открытии устройство **определяется автоматически** (`detectNewSetupPlatform()`,
  init вызывает `setPlatform(detected)`, а не хардкод Android) и сразу подбирается
  рекомендованное приложение (первое в `installData[platform]`, как правило Happ).
- **Ёмкий выбор сверху** (`.setup-picker-card`): слева заголовок «Установка», справа
  нативный дропдаун платформы `#platform-select` (с иконкой устройства
  `#platform-select-icon` из `newSetupPlatforms[].icon`, `onchange="setPlatform(...)"`);
  ниже — ряд чипов приложений `#app-selector` (`.setup-app-chip`, выбранный —
  `.is-active` с золотой рамкой, рекомендованный/первый — `.is-recommended` с точкой,
  `aria-pressed`). Дропдаун и чипы синхронизируются в `setPlatform`/`setApp`.
- **Герой** экрана — карточка инструкции (`#full-instructions-container`, рендерит
  `setApp`): заголовок «Для подключения», два коротких пункта (скачать приложение,
  затем нажать кнопку ниже) → крупная во всю ширину кнопка-CTA
  «Подключиться в 1 клик!» (`.setup-compact-cta`, шаг `type:'button'`; текст фиксированный
  для единообразия с ботом, `step.oneClickText` в компактном флоу не используется).
  Если у приложения несколько ссылок на установку, подписи строятся от имени
  выбранной программы (`formatInstallLinkLabel`): например, «FIClashX (Apple Silicon)»
  вместо абстрактного «macOS (Apple Silicon)». Промежуточные ручные шаги вроде
  «Если подписка не добавилась» в герой не выводятся, потому что ниже уже есть
  единый fallback-блок «Не сработало? Скопируйте ключ…».
  Текст пунктов, ручного fallback-копирования и блока «Подключение и использование»
  повторяет типографику вторичных пояснений кабинета
  (`text-gray-500 text-sm font-bold leading-relaxed`).
  CTA рендерится **прямым потомком** `.setup-compact-card` (вне колонки шага), на ПК
  имеет компактную ширину до 420px, а на телефоне растягивается на всю ширину для
  удобного тапа; шрифт обычного регистра (`font-weight:700`, без `uppercase`), чтобы
  не выглядеть громоздким. Предупреждения шага
  (`step.note`, напр. у Koala Clash / Prizrak-Box) выводятся приглушённым колаутом
  `.setup-compact-note`.
- Ниже, **приглушённо** — фолбэк: блок «Не сработало? Скопируйте ключ…»
  (`#setup-copy-key` + «Копировать», `copyInputValue` копирует через Clipboard API
  **без выделения** текста) и финальный шаг «Подключение и использование» (последний
  в `steps`) — `setApp` выносит его в самый низ и гасит (`.setup-compact-usage`,
  пониженный, но читаемый контраст); остальные шаги перенумеровываются автоматически.
- Все 7 платформ доступны в дропдауне (`android`/`ios`/`windows`/`macos`/`linux`/
  `androidtv`/`appletv`). Неизвестная/неподдерживаемая платформа в `setPlatform` мягко
  откатывается на Android. Старая пара всегда-видимых рядов кнопок-чипов платформ,
  свёрнутый `<details>`-селектор и большая верхняя кнопка «Скопировать ключ» удалены.

Пошаговый «мастер» с орбитой-«крутилкой» (`#new-setup-flow`, `renderNewSetupWizard`)
снова используется, но **только на телефонах и в Telegram Mini App**: на
DOMContentLoaded `applySetupFlowMode()` переключает видимость блоков
(`shouldUseSetupWizard()` — true, если `body.tg-webapp` или
`detectNewSetupPlatform()` вернул `ios`/`android`). На десктопе остаётся плоский
компактный флоу. `USE_NEW_SETUP_FLOW=true` — серверный override, форсящий мастер
для всех устройств.

Дизайн мастера повторяет паттерн конкурентов, но в наших цветах, без карточки-рамки
вокруг виджета (контент лежит прямо на фоне страницы):

- **Крутилка сверху** — постоянный DOM-блок `#new-setup-hero` (не
  перерисовывается между шагами): орб с conic-прогрессом, мягкое свечение и
  четыре статичных концентрических кольца (`.setup-hero-ring-1..4`). С каждым
  шагом кольца плавно **сужаются к центру** (масштаб/прозрачность задаются
  прямыми правилами по классу шага `setup-hero-step-*`, не CSS-переменными —
  transition на изменение унаследованной переменной срабатывает не везде;
  на финале колец нет), прогресс-дуга анимируется через
  `@property --setup-progress`, контент шага мягко проявляется
  (`setup-content-in`). Переходы отключаются при `prefers-reduced-motion`.
  На старте в орбе — иконка платформы (Apple/Android/…,
  `newSetupPlatforms[].icon`), на шагах — иконка действия
  (download/plus/check); всё меняет `updateNewSetupHero()`, на экране
  «Другое устройство» hero скрыт (`hideNewSetupHero()`).
- Под крутилкой: киккер «N из 3» (`.setup-step-kicker`), заголовок шага и
  пояснение мелким шрифтом. На мобильной ширине (≤1024px) `#new-setup-content` —
  flex-колонка высотой в экран: зона крутилки (`.setup-wizard-orb-zone`)
  растягивается, текст и кнопки прижаты к низу, как у Akenai. Блоку
  `.setup-wizard-actions` ширина задана явно (`width: 100%`), потому что
  `margin: 0 auto` у флекс-элемента отключает stretch.
- **На каждом экране ровно две компактные pill-кнопки разного цвета** (14px,
  `border-radius: 999px`): жёлтая CTA + приглушённая tonal-«Далее»
  (`.setup-secondary-btn`; правила с префиксом `.dashboard-v2 .setup-wizard-stage`,
  чтобы перебить `.dashboard-v2 .dashboard-action-btn`). Редкие fallback-ссылки
  установки (APK/.deb) — текстовые. Финальный экран «Подключение и
  использование» — одна кнопка «Завершить» → `showTab('home')`.
- **Нижний таб-бар на экране мастера скрыт** (`showTab` вешает на body класс
  `is-setup-tab`, `applySetupFlowMode` — `setup-wizard-active`; их сочетание
  прячет `.nav-mobile`). Выход — «← Назад» сверху слева
  (`.setup-devices-topbar`) на старте и на экране выбора платформы.
- Экран «Другое устройство»: центрированная сетка чипов платформ
  (`.setup-device-grid`), кнопки «Скопировать ссылку» (tonal) и «Поделиться»
  (`.setup-share-btn`, Web Share API с fallback на копирование) и QR-карта
  (`renderNewSetupQr`, qrcodejs) с `plain_subscription_url` —
  «Отсканируйте на другом устройстве».

На вкладке home компактная кнопка **«Открыть инструкцию»** находится внутри карточки
статуса рядом с автопродлением и ведёт на экран установки (`showTab('setup')`), не
занимая всю ширину на ПК.

**Кнопка «Быстрый доступ»** на вкладке home — установка кабинета как PWA / иконки на
домашний экран (`quickAccessInstall()`):
- если кабинет уже открыт как приложение (`display-mode: standalone` / `navigator.standalone`)

- Android/Chrome/Edge — нативная установка через перехваченный `beforeinstallprompt`;
- iOS Safari — модалка-инструкция «Поделиться → На экран «Домой»»;
- прочие — общая инструкция. Требует зарегистрированного `sw.js` и `manifest.json`
  (оба уже подключены в шаблоне).

### `login.html` — Вход через magic link / Telegram

Вход на сайте может создавать локальный аккаунт без RWMS-подписки. Флаг
`SITE_TRIAL_REGISTRATION_ENABLED` больше не блокирует регистрацию на сайте: он
только включает legacy-сценарий, при котором сайт сразу пытается создать RWMS trial.
Если флаг выключен, сайт создаёт только `users` и отправляет пользователя в кабинет
без активной подписки.

> Сайт работает в режиме «прямой продажи»: по умолчанию (`SITE_TRIAL_REGISTRATION_ENABLED=false`)
> сайт НЕ выдаёт бесплатный пробный период — лид сразу ведётся к оплате. Trial
> остаётся только у Telegram-бота и реферальных акций. Перед изменением этого
> поведения в проде проверьте и env-переменную, и runtime-настройку
> `site_trial_registration_enabled` в админке («Общие»): runtime-значение перекрывает env.

Telegram-вход через бота сохраняет доменный контекст через короткие start-коды.
Сайт не передаёт полный URL в Telegram: вместо этого env
`TELEGRAM_WEB_LOGIN_START_CODES` задаёт allowlist вида
`mnk-island.org|webv1,monkeyislandvpn.com|webv2,monkey-island-vpn.com|webv3`.
Рекомендуемый порядок — `domain|webvN`; для защиты от ошибки конфигурации сайт также
понимает обратный порядок `webvN|domain` и нормализует его в тот же allowlist.
Если домена нет в списке, сайт отправляет старый `web` для обратной совместимости.
В Telegram-боте тем же кодам должны соответствовать URL в
`MI_VPN_BOT_WEB_LOGIN_URLS`; `web` и `webv1` всегда означают обычный bot
`web_login_url`, который также используется для `/web`.

Онбординг из 5 слайдов (`login_onboarding_enabled` в `render_login`) показывается на
всех доменах, **кроме `cabinet`** — на cabinet-доменах главная сразу показывает форму
входа без онбординга (соответствует требованию: онбординг только на не-cabinet доменах).
Изображения слайдов переведены в WebP и лениво подгружаются.
Дополнительные ассеты `personal-server-hub` и `personal-server-lighthouse` подготовлены
с прозрачным фоном под нейтральный VPS-слоган про личный сервер для интернета, работы,
стриминга и игр.

### Лендинги и платный flow

`index_vpn.html`, `index_vps.html` и `index_vps_direct_sale.html` ведут нового
пользователя по прямому платному сценарию: лендинг → тарифы → email → `/pay/` →
payment status в текущей вкладке + Wata/YooKassa в новой вкладке → личный кабинет.
Основной CTA на лендингах ведёт к тарифам,
а вход в кабинет оставлен вторичным действием для существующих пользователей.
В шапке публичных лендингов используется анимированный бренд-знак
`engine/static/icons/monkey-island-logo-animated.gif`; исходные PNG-иконки
остаются favicon/PWA-ассетами и fallback для остальных экранов.
Hero-картинки публичных лендингов (`family-vpn.webp` и `personal-server-hub.webp`)
остаются статичными WebP-ассетами, а эффект свечения, парения и искр задается
CSS-классом `hero-art-scene`, чтобы не утяжелять первый экран большим GIF.

Перед тарифами показывается компактный trust-блок: оплата картой, доступ после
подтверждения, ссылка на email и поддержка. Формы оплаты используют
`login_link_kind=purchase_permanent`, чтобы после оплаты открыть статус платежа,
а затем залогинить пользователя постоянной purchase-ссылкой.

Контент различается по типу домена:

- **VPN-домен** (`index_vpn.html`) — открыто VPN: 4 ключевых преимущества напрямую
  (обход «белых списков», YouTube без рекламы, безлимитный трафик, до 15 устройств).
- **Нейтральные VPS-домены** (`index_vps.html`, `index_vps_direct_sale.html`) —
  **строго нейтральные формулировки про VPS** для соответствия требованиям рекламы.
  Слоган: «Личный сервер для игр, интернета и работы». Разрешено: «личный/виртуальный
  сервер», «до 10 Гбит/с», «безлимитный трафик», «до 15 устройств», «менять локацию»,
  «стриминг, игры, работа в интернете». **Запрещено** упоминать: обход блокировок,
  доступ к заблокированным сайтам, «открывайте любые сайты», рекламу/YouTube, VPN,
  цензуру, **«шифрование трафика»/приватность/логи**, а также **установку на роутеры**.
  Ориентир по тону — нейтральные VPS-лендинги (напр. vanyavps). Блок «Как это работает»
  держим коротким: после оплаты — доступ в личный кабинет с простой инструкцией.
  При правках VPS-страниц не возвращай запрещённые формулировки.

Дополнительно для конверсии:

- под каждой кнопкой оплаты — гарантия возврата денег в течение 3 дней, иконки
  платёжных систем (Visa/MC/Mir/СБП) и замок (см. также `offer.html` §5);
- тариф «3 месяца» помечен как популярный, у тарифов показывается цена за месяц
  (вычисляется через `widthratio` из реальной цены, без хардкода);
- на мобильных есть липкая кнопка покупки (`.mobile-buybar`), которая прячется,
  когда блок тарифов в зоне видимости;
- вход в кабинет демонтирован до вторичной ссылки, чтобы не конкурировать с покупкой;
- поля email используют `autocomplete="email"` и размер шрифта 16px (без зум-эффекта
  на iOS).

Производительность: hero/onboarding-изображения переведены в WebP с ресайзом
(≈ −84% веса; исходные PNG сохранены), к hero-картинкам добавлены `width/height` и
`fetchpriority`; шрифты Google Fonts и Font Awesome подключаются неблокирующе
(`preload` + `onload`), вместо рендер-блокирующего `@import`. Font Awesome
подключается версии 6.7.2 (не ниже 6.1): админка использует иконки, добавленные
в FA 6.1 (`fa-magnifying-glass-chart`, `fa-ranking-star`, `fa-chart-simple`,
`fa-envelope-circle-check` и др.) — с 6.0.0 они рендерились пустыми квадратами. Tailwind по-прежнему
подключается через CDN — перевод на собранный CSS требует Node-сборки и вынесен в
отдельную задачу.

Минимальная воронка для аналитики:
- `landing_view` — лендинг открыт;
- `tariff_cta_click` — пользователь нажал CTA к тарифам;
- `tariff_seen` — блок тарифов попал в viewport;
- `pay_click` — форма оплаты отправлена;
- `payment_widget_loaded` — WATA-форма открылась;
- `payment_success` / `payment_failed` — финальный статус оплаты.

Backend дополнительно пишет существующие события `create_invoice_*` в `event_logs`
после успешного создания invoice для пользователя.

### `offer.html` — Публичная оферта

§3 фиксирует, что бесплатный пробный период не выдаётся автоматически при
регистрации на сайте (только акции/рефералы/Telegram-бот). §3.3 отдельно
оговаривает, что платный промо-тариф «Пробный период на 3 дня» бесплатным
пробным периодом **не** является и подпадает под автопродление (§4); его цена,
как и остальные суммы оферты, подставляется из runtime-настроек БД.

§4 описывает автоматическое продление подписки. При значении системной настройки
`payment_gateway=yookassa` оплата любого доступного тарифа через YooKassa
автоматически сохраняет способ оплаты и подключает регулярные списания. Все суммы
в оферте берутся из таблицы `system_settings` по ключам `tariff_price_*` через
`get_runtime_offer_tariffs()`; это относится в том числе к `oneday`, `month` и
переходу с `threedays` на `month`. При отсутствии или некорректном значении
используется fallback соответствующей модели тарифа. Тарифы `threemonths` и
`year` продлеваются на тот же оплаченный период. Списание идёт **за 4 часа** до
конца периода (источник истины по таймингу — `monkey-island-yk-recurrent`). При
`payment_gateway=wata` покупка разовая, автопродление не подключается.
Отмена — `/cancelautopay` в боте или кнопка «Отключить автопродление» в кабинете
(`POST /cancel-autopay/`); при неудачном списании автопродление отключается без
ретраев (`monkey-island-payment`).

> ⚠️ Согласованность с кодом: текст §4 должен совпадать с фактической логикой
> включения автопродления. Enrollment выполняется в
> `monkey-island-payment/payment_handlers.py` при сохранённом способе оплаты, а
> сайт и Telegram-бот передают YooKassa `save_payment_method: True` для всех
> тарифов. При изменении этого поведения одновременно обновляйте оферту.

§5 описывает возврат
средств: возврат можно запросить в течение 3 дней после оплаты через поддержку.
Эта формулировка должна совпадать с гарантией «вернём деньги в течение 3 дней»,
которую показывают лендинги под кнопками оплаты — при изменении условий правьте
оба места согласованно.

### `terms.html` — Пользовательское соглашение (`/terms/`)

Пользовательское соглашение Telegram-бота (публичная оферта на использование
бота). Формулировка назначения бота в §2.1 подстраивается под тип домена через

## Mobile API (`mobile_api`) — авторизация мобильного приложения

Django-приложение `mobile_api` обслуживает мобильное приложение Monkey Island
(на базе hiddify/sing-box). Поддерживаются два способа входа:

1. **Telegram device-code** — бот по `/start app_<code>` сохраняет `hash(code) → user`,
   приложение меняет код на access-токен (`/auth/exchange`).
2. **Вход по email-коду** — приложение присылает email, бэкенд генерирует 6-значный
   код и отправляет письмо **синхронно тем же способом, что и magic-link** (Resend,
   с fallback на Django `send_mail`); пользователь вводит код и получает access-токен
   (`/auth/email/request` + `/auth/email/verify`).

**Эндпоинты** (`web_app/urls.py`):

| Метод/путь | Назначение |
|---|---|
| `POST /api/mobile/v1/auth/exchange` `{code}` | Обменять одноразовый код на `{access_token, subscription_url, user}` (код one-time, TTL 10 мин). Rate-limit per-IP: 90 запросов/мин (Django cache, per-process LocMemCache) → `429 rate_limited`; приложение трактует 429 как transient и продолжает поллинг |
| `POST /api/mobile/v1/auth/email/request` `{email}` | Сгенерировать 6-значный код и отправить письмо. Ответ `{ok, ttl_seconds}`. Всегда 200 для валидного email (не раскрывает, существует ли пользователь). `400 invalid_email`, `429 rate_limited` |
| `POST /api/mobile/v1/auth/email/verify` `{email, code}` | Проверить код → `{access_token, subscription_url, user}` (тот же формат, что `/auth/exchange`). `401 invalid_or_expired_code`, `429 rate_limited` |
| `GET /api/mobile/v1/me` (Bearer) | Статус подписки: `status`, `expire_at`, `days_left` (округление вверх, как в кабинете: 23ч → 1 день), `subscription_url` |
| `GET /api/mobile/v1/tariffs` | Список тарифов |
| `POST /api/mobile/v1/auth/logout` (Bearer) | Отозвать access-токен |
| `GET /app/auth-redirect?code=…` | Мост https → `monkeyisland://auth?code=…` (кнопка «Войти» в боте) |

Авторизация API — заголовок `Authorization: Bearer <access_token>`. В БД хранятся
только хэши (`sha256` с `SECRET_KEY`, как у telegram-login). Эндпоинты `csrf_exempt`
(токен-авторизация, не сессии). Выдача токена едина для обоих способов входа
(`auth._issue_access_token`).

**Email-код: параметры и безопасность.** Код — 6 цифр (`secrets.randbelow(1_000_000)`,
с ведущими нулями), TTL 10 мин, не более 5 попыток ввода на код. Rate-limit на отправку:
не чаще 1 кода в 60 сек и не более 5 кодов в час на email (определяется по свежим
строкам `email_login_codes`, без отдельного стейта). Хранится только `hash(code)`.

**Email-код: провижининг при первом входе (критично для денег).** Если по `email`
пользователь не найден — создаётся **полноценный триал, как в боте**: реальная подписка
в Remnawave через существующий sync-хелпер `engine.rwms_helpers.create_user(...)`
(`expire_at = now + SITE_TRIAL_PERIOD_DAYS`, по умолчанию 7 дней) + строка `users`.
Триал создаётся **безусловно** (НЕ зависит от `SITE_TRIAL_REGISTRATION_ENABLED`).
Перед `AddUser` username проверяется через `get_user_by_username` (должен быть `None`) —
никогда не пишем поверх чужой подписки, ничего не удаляем/не пересоздаём. Для
**существующего** пользователя RWMS не трогается вообще (ни create, ни extend).
Логика вынесена в `mobile_api/provisioning.py`. Username генерируется тем же
способом, что и в `create_site_user` (`uuid4().hex`; fallback `mi_` + `token_hex`).

**Новые таблицы БД** (в общем сабмодуле `common/models/db.py`, аддитивно — существующие
не меняются): `mobile_auth_codes` (code_hash, user_id, expires_at, used_at, source),
`mobile_access_tokens` (token_hash, user_id, revoked_at, last_seen_at),
`email_login_codes` (email[индекс, не unique], code_hash, source, created_at, expires_at,
used_at, attempts). Так как `common` — общий сабмодуль, изменение видно и боту/email-сервису.

**Отправка письма.** Код отправляется **синхронно** хелпером `engine.views.send_login_code_email`
(шаблон `emails/login_code.html`) — тем же транспортом, что и magic-link: Resend
(при `EMAIL_PROVIDER=resend`) с fallback на Django `send_mail`. Никакой очереди, Redis или
email-сервиса в этом пути нет. Если отправка упала — код не сохраняется (откат транзакции),
а `/auth/email/request` отвечает `502 email_send_failed`.

**Env-переменные.** Отдельных новых переменных не требуется — отправка переиспользует
существующие настройки писем сайта (`EMAIL_PROVIDER`, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`,
`DEFAULT_FROM_EMAIL`) — те же, что у magic-link.

> ⚠️ **Требуется миграция.** Сгенерировать штатным скриптом (не вручную):
> `./common/alembic-revision.sh "add email login codes"`, затем применить.

**Затронутые сервисы:** `common` (общий сабмодуль: добавлена модель `EmailLoginCode`),
мобильное приложение (новый UI входа по email). Письмо с кодом сайт отправляет сам
(Resend/`send_mail`), поэтому `monkey-island-email` для этого пути **не нужен**.

Тесты: `python manage.py test mobile_api` (логика кодов/токенов + эндпоинты email-входа
с моками RWMS и отправки письма, на in-memory SQLite).

## Админка: runtime-настройки

Раздел настроек в `admin_dashboard.html` управляет таблицей `system_settings`
через `support_admin_api_runtime_settings` (`engine/views.py`). Список и валидация
полностью data-driven из `common/models/settings.py` (`RUNTIME_SETTING_KEYS` +
типовые множества `INT_/POSITIVE_INT_/NON_NEGATIVE_INT_RUNTIME_SETTINGS` и т.д.):
любой ключ, добавленный в common, автоматически появляется в админке. Пустое
значение = fallback на env/default; «Сбросить» удаляет строку из БД.
Для выбора рекомендуемого Apple-приложения в боте используется enum
`apple_recommended_app`: `happ` или `incy`; отдельная миграция не нужна,
значение хранится строкой в существующей таблице `system_settings`.

Вкладка «Система» организована подвкладками (как «Аналитика»): Тарифы, Win-back,
Платёжные шлюзы, Рефералка, Алерты и Общие. Раскладка runtime-настроек по
подвкладкам задаётся константой `SETTING_GROUPS` (шаблон): `slug` группы
соответствует контейнеру `[data-settings-group]`. Ключи, не попавшие ни в одну
группу, показываются в скрытой по умолчанию карточке «Прочие» подвкладки «Общие».
В подвкладке «Рефералка» бонусные настройки и регистрационный антифрод используют
ту же рабочую ширину до `960px`, что и остальные системные настройки; антифрод
вынесен в отдельную компактную карточку без дублирования его runtime-ключей в
таблице. Сам блок антифрода собран как одна панель `.antifraud-panel` в стилистике
соседней таблицы настроек: строка = параметр, его описание, поле ввода и текущее
значение справа. Состояние автоблокировки переключается доступным тумблером
(`button[role=switch]` + `aria-checked`), параметры сохраняются одной кнопкой.
Прежние три статус-карточки убраны — лимит и окно больше не показываются дважды.
Контракт не изменился: та же форма, поля `limit` и `window_minutes`, значения
`action` = `set` / `enable` / `disable` и эндпоинт `support_admin_api_referral_antifraud`.
Так как тумблер стоит визуально первым, неявную отправку формы (Enter в поле ввода)
держит скрытая кнопка `.antifraud-implicit-submit` c `action=set` — иначе Enter
переключал бы автоблокировку вместо сохранения. Ручная блокировка реферальной
программы находится в разделе «Клиент» на подвкладке «Рефералы» и становится
доступна полному администратору только после успешного поиска клиента; там же
показываются текущий статус, причина и время изменения. На «Обзоре» остаётся только
компактная строка статуса со ссылкой на управление, поэтому действие не дублируется.
Серверные API
просмотра автоплатежей и топа оплат
сохранены для обратной совместимости, но отдельной подвкладки для них в админке нет.

### Визуальный стиль админки

`admin_dashboard.html` использует тёмную дизайн-систему Black Gold Control и
палитру клиентского ЛК: фон `#090a0f`, панели `#111217` / `#15161c`, белую
типографику и фирменный жёлтый `#ffc700` для навигации, действий и ссылок. Зелёный
и красный зарезервированы за успешными и ошибочными статусами. Интерфейс набран
Manrope с умеренной иерархией насыщенности; код и шаблоны клиентского ЛК при этом
не изменяются.
Админка также поддерживает светлую тему с белыми рабочими поверхностями, тёмной
типографикой и более контрастным золотым акцентом. Тёмная тема остаётся темой по
умолчанию. Переключатели в desktop/mobile topbar реализованы как доступные
`button[role=switch]` с `aria-checked`; Enter/Space работают нативно. На десктопе
переключатель стоит первым в группе действий, визуально выделен золотой рамкой и
показывает текущую тему подписью «Тёмная»/«Светлая». На мобильном подпись скрывается,
но тумблер и доступное название остаются. Выбор хранится только в браузере под ключом
`monkey_island_admin_theme_v1`, синхронизируется между вкладками через событие
`storage` и применяется ранним скриптом в `<head>`, до загрузки CSS. Meta/CSS
`color-scheme` и `theme-color` синхронизируются с выбранной темой, поэтому нативные
контролы и системные поверхности браузера не дают светлую/тёмную вспышку.
Подсказки всех canvas-графиков используют общие theme-aware стили: на светлом фоне
это белая карточка с тёмным текстом, а в тёмной теме — тёмная карточка со светлым
текстом; вложенные списки, выделения, код, заголовки секций и кнопка закрытия имеют
отдельные контрастные цвета для каждой темы. Маркеры серий перекрашиваются вместе с
темой: тон серии сохраняется, но берётся его `dark`- или `light`-вариант из
`CHART_TONES` (см. «Читаемость графиков»).
Визуальный override вынесен в `engine/static/css/admin_dashboard.css` и подключается
после legacy inline-стилей шаблона. Сам CSS остаётся только UI-слоем и не меняет
формы, CSRF или серверную бизнес-логику. Дополнительный read-only endpoint трафика
карточки клиента описан ниже. Миграции и новые env-переменные для оформления не
требуются. Статические файлы настроены через Django 6 `STORAGES` и
`CompressedManifestStaticFilesStorage`: `collectstatic` добавляет content hash в
URL CSS/JS. Это обязательно при недельном nginx-кеше `/static/`, иначе новый HTML
может открыться со старой версией `admin_dashboard.css`.

Табличные представления используют общий компактный skin: строки
`admin-table-row` высотой около 50px, шапки 42px с небольшим uppercase-текстом,
табличные цифры и моноширинные идентификаторы, спокойное зебрирование и sticky-шапка
на десктопе. В светлой теме шапки вынесены на отдельную нейтрально-серую поверхность
с более контрастными подписями и нижним разделителем, поэтому они не сливаются со
строками данных. Action-кнопки выделяются жёлтым, а текстовые ссылки имеют отдельный
link-цвет и подчёркивание при наведении. Skin применяется к источникам аналитики,
платежам, платежам пользователя, трафику нод и когортным таблицам; узкие экраны
сохраняют горизонтальный скролл, а основная навигация превращается в drawer.
В разделе «Найти платёж» поиск по `payment_id` / `transaction_id` расположен перед
историей платежей, чтобы форма оставалась доступна до длинной таблицы.
Списки операций в этом разделе и во вкладке «Платежи» карточки клиента используют
единый компактный журнал вместо плоской шестиколоночной таблицы: тариф и сокращённый
ID образуют основную ячейку, сумма и семантический статус читаются отдельно, а
полный ID, провайдер, пользователь и сырой результат раскрываются по нажатию на
строку. На ширине до 900px дата, провайдер и пользователь переходят во вторичную
строку без горизонтального скролла. Внутренний `support-admin/api/payments/`
дополнительно возвращает `system` и время операции; схема БД и платёжные контракты
не меняются. Прежние номера страниц удалены: они были декоративными, тогда как API
фактически загружает только последние десять операций.
Вкладка «Клиент» до первого поиска показывает полезное стартовое состояние:
поддерживаемые идентификаторы, подсказку `Enter — найти`, состав будущей карточки и
до пяти недавно найденных клиентов. Недавние клиенты сохраняются только в
`sessionStorage`, открываются повторным поиском по клику и удаляются при выходе из
админки либо закрытии браузерной сессии; серверного хранилища и нового API нет.
После поиска профиль, статус подписки, LTV, регистрация, автоплатёж и трафик собраны
в одну компактную верхнюю панель. Большая форма скрывается и заменяется действием
«Найти другого клиента». Для полного администратора первой открывается подвкладка
«Обзор»: частые операции находятся в блоке «Подписка и оплата», а временный бан и
`RWMS → DISABLED` визуально отделены в «Ограничения доступа». Смысл существующих
операций не изменён: «Подготовить возврат» устанавливает срок в один час и не
отключает автоплатёж; отключение автоплатежа остаётся отдельным действием.

Фактическое потребление загружается асинхронно через
`GET /support-admin/api/user-traffic/?q=...`. Endpoint выполняет только
`GetUserByUsername` существующего RWMS-клиента и возвращает
`used_traffic_bytes` (крупное значение за текущий период) и
`lifetime_used_traffic_bytes` (подпись «за всё время»). Запрос не изменяет и не
пересоздаёт подписку. Если RWMS не отвечает или подписка отсутствует, остальная
карточка остаётся работоспособной, а метрика показывает `—`/«Нет данных RWMS».
Старое поле `traffic` в ответе `user-payments` сохранено для обратной совместимости.
Действия runtime-настроек оформлены компактными tonal-кнопками с текстовыми
подписями: сохранение использует мягкий жёлтый акцент, а сброс остаётся нейтральным
и получает красный destructive-акцент только при наведении.

Runtime-настройки представлены как компактный реестр свойств с колонками
«Параметр», «Значение» и «Источник и действия». Тип значения показан небольшим
бейджем, булевы и enum-настройки используют список допустимых значений, секреты —
password-поле. Кнопка сохранения активируется только после изменения поля и строка
получает жёлтый индикатор несохранённого состояния; сброс недоступен, пока значение
не записано в БД. На планшетах реестр становится двухколоночным, а на телефонах —
набором компактных карточек с полноширинными действиями. На десктопе между полем
значения и метаданными источника предусмотрена дополнительная безопасная зона,
чтобы дата обновления визуально не прилипала к границе контрола.

Для одинакового поведения в актуальных Chrome, Safari, Firefox и Edge нативное
оформление `select` и стрелок числовых полей нормализовано в CSS, для Safari заданы
`-webkit-` варианты blur/appearance, а критичная раскладка настроек не зависит от
экспериментальных селекторов. Переходы на адаптивные режимы происходят на 900px и
640px; серверная валидация и API runtime-настроек остаются источником истины.

Все раскрывающиеся элементы админки имеют явный индикатор: `details/summary`
используют общий CSS-шеврон с поворотом в открытом состоянии, календарные поля —
шеврон рядом с иконкой календаря, а `select` — одинаковую SVG-стрелку вместо
зависящего от браузера нативного маркера. Для календарей синхронизируются
`aria-expanded`, `aria-controls` и состояние popover; клавиатурный фокус summary
подсвечивается фирменным жёлтым контуром.

Раздел «Рассылки» оформлен как трёхшаговый редактор: сообщение и аудитория находятся
в одной компактной рабочей области, справа показывается Telegram-предпросмотр, а
сегмент выбирается из собственного доступного dropdown вместо нативного `select`.
История отправок отображает статус, прогресс доставки и метрики воронки отдельными
ячейками; процент показывается только при ненулевом результате, поэтому значение
`0` не дублируется как `0 0%`. Изменения являются только UI-слоем и используют
существующие API рассылок, модели и таблицы без миграций.

Раздел «Промокоды» показывает правила до создания кода и в реестре. Тип `days`
сразу добавляет от 1 до 365 дней к подписке после активации; тип `discount` даёт
скидку 1–99% на первый успешный платёж после активации, после чего скидка сгорает,
а автопродление создаётся по обычной цене. Если у скидочного кода нет даты
`valid_until`, окно скидки составляет 72 часа с момента активации. Флаг
`first_purchase_only` запрещает активацию пользователям с прошлыми успешными
оплатами; без флага код доступен новым, действующим и ранее платившим клиентам.
Один пользователь может активировать конкретный код только один раз, а `max_uses`
ограничивает суммарное число активаций всеми пользователями (`0` — без лимита).

Редактор заменяет нативный выбор типа двумя доступными action-карточками и меняет
контекстную подсказку, label и допустимый диапазон значения. Форма партии теперь
также передаёт срок, комментарий и ограничение «только без оплат»; каждый код партии
по-прежнему имеет `max_uses=1`. Ответ `support_admin_api_promocodes` для партии
дополнительно содержит `promo_type`, `value`, `first_purchase_only` и `valid_until`,
чтобы список явно показывал эффект и аудиторию. Схема БД не меняется, миграция не
требуется.

Сегменты рассылок (`common/models/segments.py`, общий файл с ботом — при
изменении копировать в репозиторий бота, иначе рассылка по новому сегменту
упадёт при выборке получателей) включают win-back-пару «спящих»:
`dormant_30d_paid` — подписка истекла более 30 дней назад и были успешные
оплаты (ЮKassa или Wata); `dormant_30d_used_free` — истекла более 30 дней
назад, оплат не было, но пользователь реально подключался (есть
`user_traffic_progress.passed_0`). Сегменты не пересекаются: первый требует
наличие оплат, второй — их отсутствие. Типичный сценарий — рассылка со
скидочным промокодом по кнопке `claim_promo`.

Охват сегментов в пикере рассылок считается одним запросом
(`segments_counts_sql`): флаги «платил/автоплатёж/подключался/свежая
регистрация» вычисляются hash-join'ами за один проход по `users`, счётчики —
`count(*) FILTER` по флагам. Раньше эндпоинт гонял 18 отдельных count-запросов
с коррелированными EXISTS и на прод-объёмах не укладывался в таймаут («Сегменты
временно недоступны»). Семантика условий обязана 1:1 повторять
`ADMIN_SEGMENTS` (`SEGMENT_COUNT_CONDITIONS`, синхронность ключей — под
тестом). Быстрый путь ограничен `statement_timeout` 15s; при любой ошибке
эндпоинт откатывается на пер-сегментный подсчёт (по 5s на сегмент), а сегмент
с упавшим подсчётом отдаётся с `count: null` — пикер показывает «—» вместо
цифры и продолжает работать.

Рассылка может отключать превью ссылок: чекбокс «Отключить превью ссылок в
сообщении» (включён по умолчанию) пишется в `broadcasts.disable_link_preview`,
боты шлют такие сообщения с `disable_web_page_preview` — как `/sendmsg`.
Историческим рассылкам сохраняется прежнее поведение (превью включено).
Требуется alembic-миграция common: колонка `disable_link_preview` в
`broadcasts` (генерируется штатным скриптом миграций).

Архив рассылок: кнопка «В архив» у завершённых/остановленных строк убирает их
из основного списка истории (тестовые прогоны засоряют его), переключатель
«Архив» в шапке показывает архивные с кнопкой «Вернуть из архива». Running-
рассылку архивировать нельзя (сначала стоп). Боты архив не учитывают — они
читают только status=running. Требуется alembic-миграция common: nullable-
колонка `archived_at` в `broadcasts` (той же миграцией, что и
`disable_link_preview`).

Когортный отчёт по промокоду: эндпоинт `support_admin_api_promo_cohort`
(`/support-admin/api/promo-cohort/?promo_id=` или `?batch_id=`, роли
full/marketer, только чтение). Когорта = все активации кода
(`promo_code_uses`); для каждого пользователя считаются платежи строго после
активации (ЮKassa `succeeded` + Wata `Paid`), текущий статус подписки
(активна/истекла/блок), автоплатёж и первая покупка. Агрегаты: активации,
покупатели и конверсия, повторные покупатели и их доля среди купивших хотя бы
один раз (`second_purchase_pct`), выручка и выручка на активацию, «купили и
снова ушли», непотраченные скидки (`user_discounts` с `valid_until` в будущем),
среднее число дней до покупки, активации и первые оплаты по дням. Тарифная
аналитика объединяет ЮKassa `subscription_period` и Wata `tariff_id`, нормализует
названия и для каждого тарифа возвращает число платежей, долю и выручку; это все
успешные платежи после активации, включая повторные.
Текущее состояние когорты дополнительно разбито на взаимоисключающие категории:
активна и оплачена, активна без оплаты, истекла без покупки, ушла после покупки
и заблокирована. Отдельно — все не тестовые рассылки с кнопкой
`claim_promo` этого кода: доставлено и сколько получателей активировали код
после отправки. UI живёт в разделе «Аналитика», вкладка «Когорты промокодов»
(`subpanel-promo-cohorts`): выпадающий список промокодов и партий (данные из API
промокодов) и три представления «Обзор / Динамика / Пользователи». В обзоре
показаны четыре главных KPI (включая явную долю второй оплаты), воронка
«активация → первая оплата → повторная оплата», распределение текущих состояний,
структура оплаченных тарифов и главный этап оттока. В динамике
canvas-рендер `acqDraw` (экспортирован вкладкой «Привлечение» как
`window.acqDraw`) совмещает активации и первые оплаты; дни без событий
заполняются нулями, а для единственной даты вместо растянутого столбца
показывается состояние «мало данных». Таблица вынесена в отдельное представление,
на мобильных раскладывается в карточки и сохраняет переход в карточку клиента.
Список пользователей ограничен 500 строками, агрегаты считаются по всей когорте.
Схема БД не меняется, миграции не требуются.

Иконки проморедактора имеют отдельные контейнеры и больше не наследуют стили
вторичного текста: широкие селекторы `span` заменены на правила только для текстовой
части карточек. Значки центрируются в своих плашках и сохраняют семантический цвет,
а подписи, подсказки, чипы, правила аудитории и строки реестра используют
читаемую шкалу `9.5–17px` вместо прежних `7.5–9px`.

Вкладка «Замеры ТСПУ» имеет отдельную мобильную раскладку: форма проверки на
телефонах становится одноколоночной, связанные кнопки не расширяют контейнер, а
строки проверок и ключей RIPE Atlas отображаются карточками с подписями полей.
Сразу под блоком ключей RIPE Atlas, перед формой добавления отдельной проверки,
находится сворачиваемая массовая настройка. Администратор явно отмечает, какие
параметры применить ко всем проверкам — режим операторов/регионов, размер выборки,
ключ RIPE Atlas, расписание, TG-алерты или активность. Блок закрыт по умолчанию;
неотмеченные поля не изменяются. Обновление выполняется одной транзакцией и влияет
только на будущие запуски, не переписывая историю замеров. Десктопная табличная
раскладка сохранена.

## Админка: CustomConfigTemplate

Раздел конфигов в support-админке управляет таблицей `custom_config_templates`
через `support_admin_api_config_templates` (`engine/views.py`). Кроме JSON-шаблона,
заголовков и метаданных профиля, админка позволяет управлять `sockopt.dialerProxy`
для основного Xray outbound:

- `enable_dialer_proxy` — включает или выключает добавление `sockopt.dialerProxy`;
- `dialer_proxy_name` — имя outbound для `dialerProxy`; пустое значение означает fallback `ROUTING-IN` в custom-config.

Админка допускает несколько записей с `is_active=true`. В DB-режиме сервис
`monkey-island-custom-config` берёт все активные шаблоны и выдаёт их пользователям
по кругу в порядке `id`.

UX-детали раздела (закреплены тестами `ConfigTemplatesAdminUiTests`):

- карточки шаблонов компактные, без превью `template_json`/`additional_headers`;
  наличие дополнительных заголовков видно по бейджу «+ заголовки»;
- модалка редактирования конфига **не** закрывается кликом по фону и по Escape
  (только «Отмена»/крестик) — защита от потери несохранённого JSON;
- CodeMirror использует `material-darker` в тёмной теме и встроенную светлую тему
  `default` в светлой; выделение текста остаётся контрастным в обоих режимах.

### Персональные конфиги для пользователя (пиннинг, без миграции)

На вкладке «Конфиги» есть панель «Персональные конфиги для пользователя»
(`support_admin_api_config_pins`, `engine/views.py`, эндпоинт
`support-admin/api/config-pins/`, только роль admin). Она позволяет найти
пользователя (`username`/email/telegram_id) и отметить, какие активные конфиги ему
выдавать. Тогда сервис custom-config выдаёт этому пользователю round-robin **только
по отмеченным** конфигам, а не по всем активным.

Список конфигов рендерится компактной сеткой чипов (а не вертикальным списком):
активные показаны сразу, неактивные свёрнуты в `<details>`, сверху — фильтр по
названию и счётчик выбранных. Сохранение собирает чекбоксы из обоих списков, так
что скрытые фильтром или свёрнутые отмеченные конфиги не теряются.

Хранение — в существующей таблице `system_settings` (**миграция не нужна**): ключ
`cfg_pin:<username>`, значение — CSV из `id` шаблонов (например `3,7`). Пустой выбор
или кнопка «Сбросить (round-robin)» удаляют запись и возвращают пользователя к общему
round-robin. Тот же ключ читает `monkey-island-custom-config` в DB-режиме
(`apply_user_config_pin`): если ни один закреплённый конфиг больше не активен —
происходит fallback на round-robin по всем активным. Пиннинг ничего не меняет в
Remnawave и не трогает подписку — выбирается лишь шаблон рендера.

### Jinja-ветки в шаблонах и правила User-Agent (`client_ua_rules`)

Разные клиентские приложения по-разному переваривают одну и ту же секцию Xray-конфига
(прецедент: ядро Happ ломается на DoH-запросах через mux-outbound, а INCY при импорте
принудительно заворачивает plain-IP DNS-серверы в `direct`, что убивает DNS под белыми
списками). Поэтому `template_json` может содержать Jinja-условия по клиенту:

```jinja
"servers": [
  {% if CLIENT == "happ" %}
  "1.1.1.1",
  {% else %}
  "https://dns.google/dns-query",
  {% endif %}
  ...
]
```

Какому клиенту какое значение переменной достанется, задают правила на вкладке
«Конфиги» → «Правила User-Agent» (таблица `client_ua_rules`, эндпоинт
`support-admin/api/ua-rules/`, `support_admin_api_ua_rules` в `engine/views.py`,
только роль admin). Правило: «если User-Agent запроса подписки содержит подстроку
(без учёта регистра) → передать в рендер `variable_name=value`», например
`incy → CLIENT=incy`. Правила применяются по возрастанию `priority` (при равенстве —
по `id`), для каждой переменной побеждает первое совпадение. Имена
`VLESS_USER`/`REMARKS`/`ENTRY_NAME` зарезервированы рендером и для правил запрещены.
Если UA не подошёл ни под одно правило, переменная не передаётся и в шаблоне
срабатывает ветка `{% else %}` — она же используется старыми версиями custom-config,
поэтому «универсальный» вариант конфига должен лежать именно в `else`.

Валидация при сохранении шаблона больше не парсит сырой текст как JSON: шаблон
рендерится Jinja по сценариям — «без клиентских переменных» плюс по одному на каждое
активное UA-правило — и JSON проверяется у каждого результата
(`validate_config_template_json`). Сообщение об ошибке называет сломавшую ветку
(например, `CLIENT=incy`). При сохранении активного UA-правила все активные шаблоны
проверяются против нового набора сценариев; проблемы показываются предупреждениями,
но сохранение не блокируют. Кнопки редактора при наличии `{%` в тексте меняют
поведение: «Проверить JSON» зовёт серверную проверку без сохранения
(`action=validate` того же эндпоинта — рендерит все ветки и называет сломавшую),
«Форматировать» выравнивает отступы построчным счётом скобок без `JSON.parse`
(Jinja-строки остаются на своих местах).

Матчинг UA и передачу переменных в рендер выполняет сервис
`monkey-island-custom-config` (отдельная задача — см. его README). Таблица
`client_ua_rules` требует **миграции** (модель `ClientUaRule` в
`common/models/db.py`; миграция создаётся штатным скриптом проекта). Новая
зависимость: `jinja2` (запинена в `requirements.txt`).

Чтобы не копились висячие ключи: при удалении шаблона (`action=delete`) его `id`
вычищается из всех `cfg_pin:*` (`remove_config_template_id_from_pins`), а если у
пользователя после этого не осталось закреплённых конфигов — запись удаляется
целиком. Даже без этого выдача безопасна: `id` в `custom_config_templates` —
`Identity` и не переиспользуются, а несуществующие id отфильтровываются и в админке
(`config_pins_payload` показывает только реально существующие пины), и на выдаче
(пересечение с активными → fallback).

> Требуется миграция БД после обновления common-модели: если в базе ещё есть partial
> unique index `uix_custom_config_templates_single_active`, его нужно снять отдельной
> штатной alembic-миграцией common. Иначе PostgreSQL по-прежнему не позволит сохранить
> несколько записей с `is_active=true`.

Крупные async-блоки админки, включая аналитику за период, используют общий
`setLoading()` в `admin_dashboard.html`: он показывает центрированную орбитальную
крутилку с кольцами и песочными часами без отдельной карточки, а подпись загрузки
выводит под индикатором.

### Вкладка «MRR и рекурренты»: динамика базы и churn

`_acq_mrr` (`engine/views.py`, секция `mrr` эндпоинта
`support-admin/api/acquisition/`) показывает recognized-MRR (оплаты
«размазываются» на покрытые месяцы) и восстанавливает историю рекуррентной
базы из `event_logs` — строки `yk_recurrent_payments` при отмене удаляются,
прямой истории нет. Восстановление вынесено в чистую функцию
`_acq_recurrent_dynamics` (покрыта `AdminRecurrentDynamicsTests`):

- **активная база** — успешное автосписание за последние 12 месяцев, после
  которого не было ни отмены, ни фейла автосписания. Фейл строго после
  последнего успеха выбивает из базы (карта умерла — payment либо удаляет
  рекуррент, либо ретраит максимум ~4 суток); фейл с успешным ретраем в том же
  месяце — жив; отмена в том же месяце, что успех, консервативно — отмена;
- **отмены/churn** — кнопка «отменить автоплатёж» плюс фейлы с
  `reason ∈ {permission_revoked, recurring_permission_revoked}` (отзыв
  разрешения на стороне банка — это отмена, а не фейл). `reason` читается из
  `event_payload->>'reason'`; поле пишется payment-сервисом с августа 2026,
  у старых событий его нет.

Карточка платежа в поиске («Платежи») для YooKassa показывает тип
«Автосписание» (`yk_payments.is_autopay`) и «Причину отмены»
(`yk_payments.cancellation_reason`) — у платежей до августа 2026 оба поля
пустые/false.

### Аналитика за период: производительность и сводка

`build_admin_interval_stats` (`engine/views.py`, эндпоинт `support_admin_api_stats`)
считает когорту «первая подписка пользователя» **один раз** и материализует её во
временную таблицу `admin_cohort_events_tmp` (см. `build_admin_cohort_table`). Раньше
оконная функция `row_number()` по всему `event_logs` пересчитывалась как inline-
подзапрос в каждом из ~9 запросов аналитики, поэтому её стоимость не зависела от
длины диапазона и даже короткие периоды строились по 0.7–2 c. Теперь все запросы
(подписки, подключения, платежи YooKassa/WATA, уникальные плательщики, рефералы,
sales-series) джойнятся к лёгкой temp-таблице по `user_id` — выдача ускорена в ~5–13×
на всех диапазонах. Бизнес-логика идентична прежней: берётся только первое событие
`subscription_created` на пользователя, в когорту попадают те, чья первая подписка
лежит в выбранном `[start, end]`.

Важно про пул соединений: temp-таблица создаётся через `DROP TABLE IF EXISTS` →
`CREATE TEMPORARY TABLE`, по таблице вызывается `ANALYZE` (планировщику нужна
статистика, иначе плохие планы джойнов), а в конце расчёта она удаляется. Так как
SQLAlchemy-сессия не коммитит read-only транзакцию, при `close()` всё откатывается и
temp-таблица не «утекает» на переиспользуемый коннект.

Форма сквозного анализа (`#stats-form`) группирует быстрые периоды по смыслу:
«Текущие» (эта неделя с понедельника, этот месяц, этот год), «Прошлые» (полный
прошлый и позапрошлый календарный месяц), «Скользящие» (7/30/90/365 дней) и
«Быстро» (сегодня/вчера/история). Все кнопки по-прежнему только выставляют `start`
и `end` на клиенте и запускают существующий `support_admin_api_stats`. Детализация
графика в сквозном анализе по умолчанию — `auto`, чтобы backend сам выбирал шаг.

Карточки «Итоги» и «Тарифы» (`admin_dashboard.html`) рендерятся хелпером `statRow()`
как строки «подпись слева — значение справа» (`.stat-list` / `.stat-row`) с
разделителями и табличными цифрами вместо простого списка `label: value`. Пустые
«Тарифы» показывают `Платежей по тарифам нет`.

Карточки источников трафика (TS): все счётчики форматируются через хелпер `num()`
(`toLocaleString('ru-RU')`, разделители разрядов) — раньше форматировалась только
выручка, а счётчики выводились сырыми. Цифры выровнены `font-variant-numeric:
tabular-nums`. Статичный pill «Источник» (одинаковый на всех карточках, нёс только
шум) заменён на чип **выручки источника** (`source.revenue` через `money()`) —
раньше per-source выручка нигде не показывалась. Сетка `.sources-grid` расширена с
`minmax(300px, 1fr)` до `minmax(360px, 1fr)`, чтобы на десктопе было меньше колонок
и плитки метрик не сжимались в «стену квадратов»; `auto-fit` заменён на `auto-fill`,
чтобы одиночная карточка в последнем ряду не растягивалась во всю ширину.

Вид источников переключается между **таблицей** и **карточками** (тулбар
«Источники трафика» + сегментированный переключатель). Таблица — сравнительный вид:
колонки источник/подписки/подключения/покупатели/платежи/выручка/конв. подкл./конв.
прод., сортировка кликом по заголовку (`data-sort-key`, повторный клик меняет
направление), горизонтальный скролл на узких экранах (`.data-table`). По умолчанию на
десктопе показывается таблица, на мобилке (`max-width: 1024px`) — карточки; выбор
можно сменить вручную. Состояние (`sourcesViewMode`, `sourcesSort`,
`lastStatsResult`) и перерисовка живут на клиенте — повторного запроса к
`support_admin_api_stats` при сортировке/переключении нет. Кнопка «Подробности» в обоих
видах открывает тот же модал пользователей источника (делегирование по
`[data-source-details]`).
В карточном виде золотая кнопка «Подробности» сохраняет тёмные текст и иконку в
обычном, hover- и keyboard-focus-состояниях, включая светлую тему.
Плотные аналитические представления используют отдельную читаемую шкалу: основной
текст таблицы источников и модала пользователей — `11–13px`, заголовки инсайтов —
`16–18px`, ключевые значения — до `28px`. Высота строк и минимальная ширина таблиц
увеличены вместе со шрифтом; на узких экранах сохраняются горизонтальный скролл и
мобильная карточная раскладка модала.

Над строками источников выводится сводка «Всего» с суммами подписок, подключений,
покупателей, платежей и выручки, а также взвешенными конверсиями. Детализация
источника открывается в компактной табличной модалке: идентификаторы пользователя,
срок подписки, платёжный и VPN-статусы помещаются в одну строку; на телефонах строка
перестраивается в карточку. Сводка и сортировка рассчитываются в браузере из уже
полученного ответа и не создают дополнительных запросов.

Переключатель продаж в сквозном анализе имеет два режима. «Новые клиенты» оставляет
платежи, покупателей, выручку и тарифы когортными; «Все платежи» заменяет только эти
кассовые KPI абсолютными итогами из тех же бакетов, что показаны на графике.
Подписки, подключения, источники и конверсии воронки при этом остаются когортными.
В ответ `sales_series` добавлено обратно-совместимое поле `totals`; схема БД и
соседние сервисы не меняются.

### Когортный анализ (раздельные окна когорты и графика)

Эндпоинт `support_admin_api_cohort_stats` (`engine/views.py`, маршрут
`support-admin/api/cohort-stats/`, только для роли admin) и блок «Когортный анализ»
на вкладке «Аналитика» (`admin_dashboard.html`, форма `#cohort-form`, контейнер
`#cohort-result`) — отдельный график **поверх** обычной аналитики, существующий
`support_admin_api_stats` он не меняет.

Отличие от `build_admin_interval_stats`: там окно когорты и окно графика — это один и
тот же интервал. В когортном анализе они **разделены**:

- **Диапазон** `[start, end]` — внешний период (например, весь 2025 год).
- **Когорта** `[cohort_start, cohort_end]` — окно **внутри** диапазона (например,
  январь). В когорту попадают пользователи, чьё **первое** событие
  `subscription_created` лежит в этом окне.
- График строит платежи этой когорты на **всём** внешнем диапазоне — видно, что
  осталось от январских клиентов на горизонте года.

Реализация переиспользует существующие хелперы без изменений: `build_admin_cohort_table`
(материализация когорты во временную таблицу `admin_cohort_events_tmp` по **окну
когорты**) и `build_admin_sales_series` в режиме `cohort` (серия по **внешнему**
периоду). Сводка `build_admin_cohort_retention_stats` дополнительно считает размер
когорты, число покупателей, платежи, выручку, конверсию, ARPU/ARPPU и разбивку по
источникам трафика. Окно когорты на сервере зажимается в границы диапазона
(`admin_clamp_cohort_window`); если пересечения нет — ответ `400`.

**Рефералы, приведённые когортой.** Сводка считает, сколько новых пользователей
**привели** члены когорты: `invited_referrals` — пользователи с `referred_by_id`,
указывающим на члена когорты (join по temp-таблице); `invited_referrals_active` и
`invited_referrals_paid` — из них начали пользоваться (бонус `TRAFFIC`) и оплатили
(бонус `PURCHASE`), по `ReferralBonus.referrer_id` в когорте. Это обратное направление
к `build_admin_interval_stats`, где считается, сколько членов когорты сами пришли по
реферальной ссылке. Метрики выводятся отдельными плитками, в график не идут (это
агрегаты за весь период, а не временной ряд), поэтому скорость отрисовки не страдает.

**UI «Аналитики» разбит на под-вкладки** (`#panel-stats .subtabs`): «Сквозной анализ»
(`#subpanel-overview` — прежний `support_admin_api_stats`) и «Когортный анализ»
(`#subpanel-cohort`). Переключение — `showStatsSubtab()`, авто-загружается только
сквозной; когортный строится по кнопке «Построить».

Под формой когорты есть сворачиваемый блок-глоссарий `.metrics-legend`
(`<details>/<summary>` «Как читать показатели») с определениями всех показателей
(Размер когорты, Покупатели, Платежи, Выручка, Конверсия, ARPU, ARPPU, Привела
рефералов / активны / оплатили, График) — видимый текст (не только hover-`title`),
поэтому читается и на мобильных.

Параметры запроса: `start`, `end`, `cohort_start`, `cohort_end` (`YYYY-MM-DD`),
`granularity` (`auto|day|week|month`, по умолчанию `month`). По умолчанию диапазон —
последние 12 месяцев, когорта — первый месяц. В форме `#cohort-form` выбор разбит
на две отдельные группы: «Диапазон графика» (`start`/`end` + быстрые пресеты
`data-cohort-period`: этот/прошлый/позапрошлый год, 12 мес., всё время —
**«Всё время» начинается с апреля 2025**, старта бизнеса, см. `COHORT_BUSINESS_START`)
и «Когорта» (`cohort_start`/`cohort_end` + быстрые пресеты `data-cohort-window`:
7 дней/30 дней/90 дней/до конца месяца). Все пресеты когорты выставляют начало
когорты равным `start` внешнего диапазона; «до конца месяца» заканчивается последним
днём календарного месяца, в котором лежит `start`. Детализация (`granularity`) и
кнопка «Построить» вынесены ниже этих групп, чтобы не смешивать выбор окна графика
и окна когорты. При ручном выборе даты подсветка соответствующих быстрых пресетов
сбрасывается.
График **не** строится автоматически при загрузке страницы (чтобы не запускать
тяжёлый запрос одновременно с основной аналитикой) — админ нажимает «Построить».

Графики в обеих подвкладках «Аналитики» переиспользуют единый
`drawSalesSeriesChart` в стилистике графика «Новые vs повторные»: денежные столбики
складываются из выручки по тарифам (левая ось), контрастная линия показывает уникальных
покупателей (правая ось). При наведении подсвечивается весь период, появляется
вертикальная направляющая, активная точка и общий `bindSalesChartTooltip` с выручкой,
платежами, покупателями и разбивкой по тарифам. На мобильной ширине плотные дневные
ряды не сжимаются, а прокручиваются горизонтально. Для месячной детализации
когортный tooltip по-прежнему показывает месяц словом («Декабрь 2025» вместо
«12.2025», хелпер `cohortBucketLabel`). Палитра серий вынесена в общий объект
`CHART_TONES` (по одному тону на серию, с вариантами `dark`/`light`). Тона намеренно
разнесены по цветовому кругу — индиго, янтарь, зелёный, фиолетовый, оранжевый,
графитовый, голубой, розовый: в стеке из 5-7 тарифов соседние сегменты должны
отличаться тоном, а не только светлотой. Золотая тема интерфейса остаётся в рамках
и акцентах, но на серии данных не распространяется. Тёмная тема использует
исторические значения (`rgba(120,140,255,.75)`, `rgba(255,199,0,.9)`,
`rgba(90,220,150,.95)`, `#9b6dff`, `#f5b85b`, `#d8dde8`, `#38bdf8`, `#f472b6`);
для светлой подобраны затемнённые аналоги тех же тонов — контраст каждого не ниже
3:1 на белом фоне. `acquisitionChartColors` / `tariffChartColors` и их `*Light`-двойники
теперь производные от `CHART_TONES`, поэтому источник правды один.
Серия хранит имя тона (`tone`), а не готовую строку цвета, и резолвится лениво
через `adminChartSeriesColor` на каждой перерисовке — переключение темы
перекрашивает уже построенные графики без повторного API-запроса.
Backend-серия и API-контракты не менялись.

#### Читаемость графиков

Служебные цвета «обвязки» графика живут в `adminChartUiColor` и одинаковы для обоих
canvas-рендереров (`drawSalesSeriesChart` и `acqDraw`):

- подписи осей и легенда подняты по контрасту (было `.62`/`.7` — данные читались
  лучше собственных подписей);
- нулевая линия рисуется токеном `gridStrong`, остальная сетка — `grid`: от базовой
  линии считываются высоты столбиков;
- сегменты стека разделяются волосяной линией `barSeparator` (в тёмной теме тёмной,
  в светлой — белой), иначе соседние тарифы читаются как один сплошной столбик.

Подписи делений формирует общий `adminChartAxisLabel`: суммы от 10 тыс сокращаются
до «48 тыс», от миллиона — до «1,2 млн», проценты получают знак `%`. Без этого
крупные суммы не помещались в отступ оси и налезали на область построения.

Плотность подписей оси X считается по реально измеренной ширине текста
(`ctx.measureText`), а не по фиксированному «каждая n/14». Последняя подпись
по-прежнему рисуется всегда, но пропускается, если наезжает на предыдущую.

Легенда `acqDraw` раскладывается по строкам хелпером `acqLegendRows` под ширину
канвы, и верхний отступ области построения считается от числа строк — на узком
экране легенда больше не уезжает за правый край.

Тултипы вкладки «Привлечение» используют `acqFmtValue`: разделители тысяч во всех
метриках (включая штучные) и явная единица измерения — `₽` или `%`. Название и
значение разнесены по краям строки, цифры моноширинные (`.acq-tooltip-value`).

Текстовые сводки под графиками окрашиваются классами `.chart-tone-*`
(`amber`/`indigo`/`green`/`pink`/`strong`) вместо инлайновых `style="color:…"`:
у каждого есть светлый вариант, поэтому цифры перекрашиваются вместе с темой
(раньше `#fff` на светлой теме был не виден).

В разделе «Привлечение» над под-вкладками расположен раскрывающийся справочный блок
`#acq-new-revenue-help`. Он фиксирует пользовательскую семантику метрик: «Новый
покупатель» определяется по самому раннему успешному платежу пользователя в
объединённой истории Wata и YooKassa; «Выручка новых» содержит только сумму таких
первых платежей в периоде по МСК, а последующие продления относятся к повторной
выручке. Там же явно указано, что значения пересчитываются из текущей БД и что
`Подписка→покупатель` в воронке сопоставляет недельные агрегаты, а не строит строгую
когорту по неделе создания подписки. Расчёт и API не менялись — добавлено только
пояснение в админском интерфейсе.

В таблице воронки рядом с `Подписка→покупатель` есть колонка `Инвойс→Оплата` —
все оплаты недели ÷ созданные за неделю инвойсы. Это тоже сопоставление недельных
итогов: оплата могла пройти по счёту конца прошлой недели, а в числителе есть
продления, поэтому значение может превышать 100%. Считается на клиенте из полей
`payments` и `invoice_clicks` ответа `funnel` — API не менялся.

На под-вкладке «Новые vs повторные» период графика выбирается тремя способами:
пресетом (30/60/90 дней), переключателем месяцев (`#acq-newrep-month`, список
последних 18 месяцев; выбор месяца подставляет его границы в календарные поля)
или произвольным диапазоном через календарные поля дат. Итоговая строка под
графиком показывает суммы за весь выбранный период: выручка новых и повторных,
доля новых, итого и число новых покупателей.

Ниже расположен график «Отвал базы» (секция `renew45` эндпоинта
`support-admin/api/acquisition/`): для каждого месяца берётся когорта плативших
за короткие тарифы (день/3 дня/неделя/месяц), и считается доля тех, кто в
течение 45 дней после своей последней оплаты в месяце сделал любую следующую
оплату (включая апгрейд на длинный тариф). Длинные тарифы (3/6/12 мес) в когорту
не входят — их окно продления заведомо длиннее 45 дней. Месяцы с ещё не
закрытым 45-дневным окном помечаются `mature=false` и на линии процента не
показываются, чтобы не занижать удержание.

График «Подписки по дням и конверсия в первую оплату» (секция `trials`
эндпоинта `support-admin/api/acquisition/`) принимает параметр `window` —
окно конверсии в днях: 10 (по умолчанию), 30 или 60; другие значения молча
приводятся к 10 (допустимый набор — `ACQ_TRIALS_WINDOWS` в `engine/views.py`).
Ответ содержит `window_days`, фронт подставляет его в подпись линии. Селектор
окна — `#acq-trials-window` над графиком. Чем шире окно, тем длиннее
«недозрелый» правый хвост линии: у когорт моложе окна процент ещё дорастёт.

Таблица «Эффективность winback/истечений» (вкладка «Пуши», секция `pushes`
эндпоинта `support-admin/api/acquisition/`) считает конверсию по **last-touch
атрибуции**: окна 72 часов у пушей серии (3-days-left → 1-day-left →
subscription-expired → winback-N) перекрываются, поэтому каждая оплата
привязывается только к последнему продающему пушу перед ней, а каждый пуш
засчитывается сконвертившим не более одного раза (по первой атрибутированной
оплате). CTE атрибуции вынесен в `ACQ_PUSH_ATTRIBUTION_CTE` (`engine/views.py`).
Помимо конверсии таблица показывает сегменты сконвертившихся: «Новые» (это была
первая оплата пользователя за всю историю Wata+YooKassa) и «Повторные», медиану
часов от пуша до оплаты, атрибутированную выручку и распределение чеков
(по сумме платежа виден купленный тариф). Только читающие запросы — схема БД и
запись событий не менялись.

«Отправлено» и дневной график пушей дедуплицируются: каждый пуш логируется
событием `notification_sent` каждым ботом бренда отдельно (vpn- и vps-бот
читают свои копии очереди и пишут в общий `event_logs`), поэтому считаются
уникальные `(user_id, день)` для таблицы и `(user_id, тип)` в разрезе дня для
графика, а не сырые строки. Исторические события до фикса бота (до 08.2026)
дополнительно содержат недоставленные пуши (бот логировал `notification_sent`
и при «бот заблокирован») — с фикса `SendStatus` в боте событие пишется только
при реальной доставке.

С 08.2026 событие `notification_sent` пишет и email-канал
(`monkey-island-email`, при успешно принятой Resend'ом отправке письма) — в
`event_payload` у него `channel="email"`, у ботов `channel="telegram"`
(legacy-события без поля `channel` — telegram). Атрибуция и «Отправлено»
каналы не различают и считают оба: письмо и пуш одного типа одному юзеру в
один день схлопываются той же дедупликацией `(user_id, день)`, а оплаты
email-only пользователей (без Telegram) теперь тоже атрибуцируются.
При необходимости разрез по каналам можно строить по
`event_payload->>'channel'` без изменения схемы.

Под-вкладка «Путь клиента» (секции `trial_timing`, `renewal_ladder` и
`tariff_paths` эндпоинта `support-admin/api/acquisition/`) отвечает на вопрос
«на каком этапе конвертятся и удерживаются клиенты»:

- **Когда платят первый раз** (`trial_timing`) — распределение дня первой оплаты
  относительно старта триала (первое событие `subscription_created`
  пользователя): бакеты 0–1, 1–2, …, 60+ дней. Видно, какая доля покупает
  импульсно, какая — в зоне пушей об окончании триала, в момент истечения и
  сильно позже (winback-серия). Период когорты выбирается селектором
  (90/180/365 дней или вся история).
- **Лестница продлений** (`renewal_ladder`) — по когортам месяца создания
  первой подписки (МСК): привлечено → оплатили ≥1 раз → ≥2 → ≥3 → ≥4. Первая
  ступень показывается в процентах от привлечённых, каждая следующая — от
  предыдущей ступени. Свежие когорты дозревают, их проценты растут со временем.
- **Переходы между тарифами** (`tariff_paths`) — для каждого тарифа: сколько
  пользователей впервые купили его за окно (по умолчанию 12 месяцев), у скольких
  это была самая первая покупка в жизни, и с какого тарифа пересели остальные
  (тариф платежа непосредственно перед первой покупкой данного тарифа —
  `lag()` по объединённому потоку Wata+YooKassa, CTE `ACQ_PAYS_TARIFF_CTE`).

Все три секции — только читающие запросы; схема БД не менялась.

### Вкладка «Реклама»: импорт CSV Яндекс Директа и экономика по дням

Траты на рекламу (`ad_spends`, одна строка = день × канал × аккаунт) можно
вводить руками или загружать CSV-выгрузкой «по дням» из кабинета Яндекс Директа
(колонки «День», «Показы», «Клики», «Расход, ₽»; строка «Итого» и подвал
игнорируются). Импорт идёт через эндпоинт
`support-admin/api/acquisition/ad-spends/` (`action=import_csv`, multipart с
полем `file`, опционально `channel` — по умолчанию `yandex-direct`, и
`account` — по умолчанию `default`). Загрузка **идемпотентна в разрезе
аккаунта**: upsert по уникальному ключу `(day, channel, account)` — повторная
загрузка того же файла перезаписывает те же дни того же аккаунта, а данные
других аккаунтов за эти дни не трогаются; в аналитике траты по дню суммируются
по всем аккаунтам. Это позволяет лить трафик с нескольких кабинетов Директа и
выгружать статистику каждого без затирания: в админке сверху вкладки «Реклама»
есть селектор аккаунта с кнопками «+ Добавить аккаунт» и «Переименовать»
(список собирается из данных, эндпоинт отдаёт его полем `accounts`).
Переименование (`action=rename_account`, поля `from`/`to`) массово переносит
строки аккаунта на новое имя — типовой случай: данные, залитые до появления
мульти-аккаунтов, лежат под `default`, и их можно объявить конкретным
кабинетом перед дозаливкой второго. Если у целевого имени уже есть строки за
пересекающиеся `(day, channel)`, операция прерывается с 409 — ничего не
затирается. Кодировки: UTF-8 (с BOM) и
cp1251; числа с запятой-разделителем и пробелами-разрядами парсятся.

Модель `AdSpend` получила nullable-колонки `impressions`/`clicks` (из CSV; при
ручном вводе NULL) и NOT NULL-колонку `account` (default `'default'`) с новым
уникальным ключом `uq_ad_spends_day_channel_account` — **требуется
alembic-миграция в common** (autogenerate по модели). До наката вкладка показывает плашку
`needs_migration`, старые секции продолжают работать.

Секция `ads_daily` эндпоинта `support-admin/api/acquisition/` (параметры
`days`, `group=day|month`) отдаёт экономику привлечения по дням МСК или по
месяцам: расход/показы/клики, CPC = расход ÷ клики, созданные подписки,
подключения (первый трафик по подписке — событие `traffic_threshold_reached`
c `threshold=0`, та же метрика, что в разделе «Аналитика»), продажи (новые
покупатели — первая оплата в объединённой истории Wata+YooKassa) и три ступени
стоимости: **цена подписки**, **цена подключения**, **цена продажи** (расход ÷
соответствующий счётчик). Единый столбец CPA убран — вместо него три ступени.
При группировке по месяцам делятся месячные суммы, а не усредняются дневные
значения. Во вкладке «Реклама» это два графика (расходы + воронка; линии
стоимостей) и таблица с переключателем «По дням / По месяцам». Недельная
таблица эффективности дополнена подключениями и ценой подключения. Табличная
детализация двух графиков визуально отделена от canvas-блоков собственным
заголовком и пояснением, показывает доступные направления прокрутки, использует
видимый scrollbar, градиентный край и закрепляет шапку/первый столбец внутри
ограниченной по высоте области.

### Win-back настройки

Группа **Win-back** конфигурирует кампанию возврата истёкших пользователей
(сервисы user-notify/bot/payment/email):

- `winback_enabled` — общий тумблер цепочки (bool). Выключение переводит
  user-notify на legacy-путь: одно «подписка истекла» на пользователя, без
  drip-серии и без скидочных офферов (уже выданные офферы гасит ре-валидация).
  Значение перечитывается нотификатором каждый цикл, рестарт не нужен. Дефолт
  Monkey Island — включено (стартовое значение бота `1`, env нотификатора
  `MI_UN_WINBACK_ENABLED=true`).
- `winback_price_month`, `winback_price_threemonths`, `winback_price_year` — сниженные
  цены тарифов в win-back витрине (на витрине «все тарифы» месяц показывается по
  регулярной цене, скидка — только на 3 и 12 мес.).
- `winback_send_hour_start`, `winback_send_hour_end` — окно отправки (часы МСК).
- `winback_offer_ttl_hours` — срок жизни персонального оффера (`winback_offers`).
- `winback_grace_hours` — грейс после истечения оффера, в течение которого скидку
  ещё разово отдают.

Чтобы группа отобразилась, в `common` сайта должны присутствовать win-back ключи
из `common/models/settings.py` — пропагируйте common, как и для остальных сервисов.

## Админка: Трафик нод (поиск расшаренных подписок)

Вкладка «Трафик нод» (только роль admin) показывает потребление трафика
подписками на конкретной ноде Remnawave или суммарно по всем нодам — для
поиска «утёкших» (расшаренных) подписок по аномально высокому объёму. При первом
открытии вкладки за текущую загрузку страницы автоматически строится отчёт по
всем нодам за сегодня (UTC); повторное переключение вкладок не запускает новый
тяжёлый запрос. Фильтры и кнопка «Показать» позволяют вручную перестроить отчёт.

Клиентский `renderNodeTraffic()` оформляет результат в общей дизайн-системе
админки: отдельная сетка сводных метрик, информационная полоса исключённых
служебных подписок и таблица с собственной шапкой. В строках используются ранги,
статусные чипы, индикатор доли, структурированная топ-нода и визуальный маркер
аномалии при доле от `10%`. Длинные идентификаторы и названия нод обрезаются с
полным значением в `title`; на узких экранах таблица прокручивается горизонтально.

Эндпоинты (`engine/views.py`, логика агрегации в `engine/node_traffic.py`):

- `GET /support-admin/api/traffic-nodes/` — список нод панели;
- `GET /support-admin/api/node-traffic/` — отчёт по потреблению. Параметры:
  `node` (`all` или uuid ноды), `hours` (период от текущего момента назад,
  по умолчанию 24, максимум 90 дней), `top` (строк в ответе, максимум 500),
  `min_gib` (порог трафика).

Важно: панель хранит трафик посуточно (одна строка на ноду/пользователя/
календарные сутки UTC, `created_at = 00:00` дня), а выборка фильтрует
`created_at >= start`. Начало периода внутри дня отбрасывало бы весь этот
день, поэтому `build_report` выравнивает начало вниз до полуночи UTC
(закреплено тестом `NodeTrafficDayGranularityTests`; инцидент 2026-07-10:
отчёт «за 24 часа» в 01:36 UTC показывал только 1.6 часа данных). Часовой
точности у статистики нет — `hours` лишь выбирает календарные дни.

Данные получаются через rwms (read-only RPC `GetNodes` /
`GetNodeUsersUsage` / `GetUserByUuid`), напрямую в панель сайт не ходит,
ничего не изменяет и не удаляет. Особенности:

- служебные подписки (по умолчанию `SYS-REROUTE`) исключаются из выборки и
  totals; список расширяется env-переменной `TRAFFIC_STATS_EXCLUDE_USERS`
  (username через запятую);
- ноды опрашиваются с низкой параллельностью (3), т.к. панель отвечает
  HTTP 500 на тяжёлые запросы длинных периодов; не ответившие ноды
  возвращаются в `failed_nodes`, и вкладка явно показывает, что данные
  неполные;
- для показанных строк подтягиваются карточки пользователей (статус, дата
  окончания, HWID-лимит, telegram id);
- в режиме «все ноды» у каждого пользователя показывается топ-нода и её
  доля в его трафике.

Покрыто тестами `NodeTrafficReportTests`, `NodeTrafficAdminApiTests`,
`NodeTrafficTemplateTests` (`engine/tests.py`).

## Админка: Установка нод (автоматический provisioning)

Вкладка «Установка нод» (только роль admin) автоматизирует ручной процесс
«зайти по SSH и выполнить install-скрипт». Поток:

1. Админ один раз заливает в БД копии install-скриптов из devops-репозитория
   (блок «Скрипты установки», по одному на тип ноды: `self_steal`,
   `hysteria`, `whitelist`, `whitelist_self_steal`). Правка создаёт новую
   версию с историей и откатом; активна ровно одна версия на тип. Пока
   скрипта нет, вкладка пишет «задай скрипт» и не даёт создать заявку.
   Эталонные скрипты в devops-репозитории не изменяются.
2. «Новая нода»: имя, тип, нода-образец (с неё снимается конфиг-профиль
   панели) → заявка + одноразовый токен (показывается один раз) и команда
   `curl -fsSL https://<панельный-домен>/node-bootstrap/runner/ | bash -s -- <токен>`.
3. На свежем сервере обёртка делает claim (фиксация IP, выдача `SECRET_KEY`
   панели через RWMS `GetNodeSecret`, идемпотентное создание ноды в панели
   через RWMS `CreateNode`), скачивает зафиксированную версию скрипта
   (sha256 сверяется), запускает установку и стримит лог/стадии.
4. Страница заявки показывает чеклист стадий (claim → script → connect) и
   хвост лога; когда панель видит коннект remnanode, заявка становится
   `ready`. Сертификаты в поток не входят — их деплоят вручную
   (`manage-node-certificates.sh deploy --host <ip>` из devops-репозитория,
   там же нода добавляется в инвентарь для автопродления), после чего на
   ноде включается nginx (install-скрипт сам подсказывает команды, если
   сертов ещё не было на момент установки).

Интерфейс вкладки разделён на два самостоятельных рабочих режима:

- «Установки» — четырёхшаговая схема процесса, подписанная форма создания,
  зафиксированная версия профиля и компактный список заявок со статусом и
  деталями;
- «Скрипты» — список профилей и один выбранный редактор вместо нескольких
  длинных полей подряд. Редактор остаётся обычным `textarea` (в API уходит
  исходный Bash без преобразований), но поверх него синхронно рисуются номера
  строк и подсветка shebang, комментариев, ключевых слов, команд, переменных,
  строк и опций. Подсветка и адаптивная раскладка работают в светлой и тёмной
  темах; переключение профиля предупреждает о несохранённых изменениях.

Безопасность: токен хранится только sha256-хешем, TTL до claim —
`NODE_BOOTSTRAP_TOKEN_TTL_MINUTES` (60), после claim привязан к IP;
`SECRET_KEY` не логируется; нода в панели только создаётся, удаления в
этом потоке нет (Remnawave Safety Rules — висящую ноду от неудавшейся
установки удаляют руками в панели).

Admin-эндпоинты (`engine/views.py`, логика в `engine/node_provisioning.py`):

- `GET/POST /support-admin/api/node-scripts/` — список/сохранение
  (`action=save`, с мягкими предупреждениями об интерактивном `read` и
  отсутствии shebang) и активация версий (`action=activate`);
- `GET/POST /support-admin/api/node-provision/` — список заявок + данные для
  формы; `action=create|revoke`;
- `GET /support-admin/api/node-provision/detail/?id=` — стадии, лог,
  авто-перевод в `ready` по коннекту ноды.

Публичный bootstrap-API (Bearer-токен заявки, **отвечает только на доменах
из `NODE_BOOTSTRAP_DOMAINS`**, на прочих — 404; пустой список = выключено):

- `GET /node-bootstrap/runner/` — обёртка (шаблон
  `node_bootstrap_runner.sh`);
- `POST /node-bootstrap/claim/` — конфиг + `secret_key` + `script_sha256`;
- `GET /node-bootstrap/script/` — зафиксированная версия скрипта;
- `POST /node-bootstrap/progress/` — `{stage, status, message, log_tail}`;
- `POST /node-bootstrap/complete/` — `{exit_code}`.

Новые env-переменные: `NODE_BOOTSTRAP_DOMAINS` (csv, обязательно для
работы фичи; это НЕ домен панели Remnawave — любой домен, который
маршрутизируется на сайт с валидным TLS, например отдельный поддомен:
свежие ноды забирают с него скрипт и секреты по публичному HTTPS),
`NODE_BOOTSTRAP_TOKEN_TTL_MINUTES` (60).

⚠️ **Требуется миграция** (таблицы `node_install_scripts`,
`node_provision_requests`, `node_provision_stages`) — генерируется штатным
`./common/alembic-revision.sh`. Также требуется RWMS с методами
`GetNodeSecret`/`CreateNode` (деплой RWMS раньше сайта).

Покрыто тестами `engine/tests_node_provisioning.py` (версии скриптов,
токены/TTL/IP-binding, стадии, host-gating, admin-API) и
`NodeProvisionTemplateTests` в `engine/tests.py` (структура режимов,
Bash-редактор и мобильная раскладка).

## Полная блокировка пользователя (user_blocks)

Пользователи с записью в таблице `user_blocks` (ставится ботом командой
`/block-user`) не могут пользоваться сайтом:

- `engine/user_block_middleware.py` (`UserBlockMiddleware`, стоит после
  `AuthenticationMiddleware`) разлогинивает заблокированного на любом запросе и
  показывает страницу логина с сообщением о блокировке (403);
- `pay` отклоняет создание платежа с 403 — в том числе анонимную оплату по
  email заблокированного (иначе успешный платёж реактивировал бы отключённую
  подписку);
- мобильный API: `mobile_api/auth.py` не аутентифицирует заблокированных
  (Bearer-токены перестают работать) и не выдаёт новые токены при
  `auth/exchange`.

Общий хелпер — `engine/user_block.py` (`is_user_blocked`). Модель `UserBlock`
живёт в common; для таблицы нужна миграция common.

## Деплой

Смотри `docker/website/PRODUCTION.md` и `docker/edge/PRODUCTION.md`.

В образ сайта входит Node.js и npm-пакет `@incy/link-encoder`
(`package.json`, ставится на этапе сборки): `engine/incy.py` шифрует ссылку
подписки для приложения Incy (`incy://crypt1/...`), когда в админке
`apple_recommended_app = incy` — тот же энкодер, что в телеграм-боте. При
недоступности энкодера кабинет молча откатывается на Happ.

Конфиги: `docker/website/docker-compose.yml` + `nginx.conf.template`.
Origin deploy и renew сертификата не должны выполнять `docker compose down`, чтобы ошибка certbot или загрузки образа не оставляла сайт выключенным и не удаляла compose-логи.


## Зависимости

Все прямые зависимости в `requirements.txt` запинены на точные версии (инцидент 2026-07-07: незапиненный `remnawave` в rwms при пересборке Docker-образа притянул 2.8.0 с breaking change, и бот показывал всем пользователям, что срок ключа истёк). Пересборка образа не должна молча подтягивать новые версии. Обновление любой версии — осознанное изменение: поднять пин в `requirements.txt`, прогнать тесты и проверить согласованность со смежными сервисами.
